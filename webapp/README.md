# Веб-панель BR Management

Второй "фронт" к тому же боту — та же Google-таблица, та же система ролей
(`utils/access.py`), тот же канал логов. Бот и сайт работают ОДНОВРЕМЕННО,
не заменяют друг друга.

## Вход на сайт

ВК ID + пароль (как просили) — без Telegram Login Widget. Пароль:
- Устанавливается/меняется в **боте** командой `/setpassword ваш_пароль`.
- Хранится ТОЛЬКО на сайте (локальная SQLite-база, `webapp/db.py`) — в
  Google-таблицу не попадает вообще, даже в виде хэша.
- Никто, включая создателя, не может "посмотреть" чужой пароль — только сбросить
  на новый (кнопка в панели управления: старшим следящим — для своего
  направления, создателю — для кого угодно).
- При входе с нового устройства/браузера/IP пользователю приходит уведомление
  в Telegram с IP и данными браузера — на случай если это не он.

## Что уже полностью работает
- Вход (ВК ID + пароль), сброс пароля через бота.
- Профиль / Статистика.
- Заявления: Отчёт (с распознаванием, начислением баллов, антидублем и алертами
  в Telegram точно как в боте), Неактив, Доп.работа, Снятие наказаний.
- Админ: Список пользователей, Добавить пользователя.
- Инструменты: /members. (/id намеренно НЕ на сайте — остаётся только в боте,
  доступной вообще всем, как и раньше.)

## Иерархия доступа (все роли, бот и сайт)

Кто угодно с ролью может управлять (снимать/выдавать доступ, менять баллы,
наказания, смотреть чужую статистику, логи, решать заявки) **только строго
нижестоящими по роли людьми и только в своей зоне ответственности**:
Лидер/Следящий — своя организация, Старший следящий — своё направление,
Руководство и Создатель — без ограничений. Равных себе и вышестоящих трогать
нельзя никому, кроме Создателя. Это проверяется как при показе списков (что
видно в интерфейсе), так и заново при самом действии на сервере — чтобы
отправка формы напрямую (не через кнопку) не давала обойти правило.
См. `can_manage()` / `manageable_users()` / `visible_orgs()` / `max_grantable_role()`
в `utils/access.py` — это общие для бота и сайта функции.

## Тесты (аттестации)

Следящий и выше могут создавать тесты (раздел "Тесты" в меню сайта):
- **Следящий** — тест виден только его организации.
- **Старший следящий** — либо всему своему направлению разом, либо отдельной
  организации из направления.
- **Руководство/Создатель** — всем организациям, отдельному направлению или
  отдельной организации.

Вопросы добавляются/удаляются динамически (кнопки "+ Вопрос" / "✕"). Люди с
ролью Старший состав/Лидер из назначенной организации при входе на сайт сразу
видят тест и не могут пользоваться остальным сайтом, пока не ответят на все
вопросы ("Следующий вопрос" → ... → "Готово"). Если человек сворачивает
вкладку или переключается на другую во время теста — попытка сбрасывается,
а следящему его организации, старшему следящему направления, руководству и
создателю приходит уведомление в Telegram. Результаты (раздел "Результаты
тестов") видно в той же зоне ответственности: следящему — только свою
организацию, старшему следящему — своё направление, руководству/создателю —
всех.

## Деплой на Railway (второй сервис в том же проекте)

1. В том же Railway-проекте, где уже крутится бот: **New → GitHub Repo** →
   выбери тот же репозиторий ещё раз (второй сервис из того же кода).
2. У этого нового сервиса в **Settings → Deploy** укажи команду запуска:
   ```
   uvicorn webapp.app:app --host 0.0.0.0 --port $PORT
   ```
3. **Settings → Networking → Generate Domain** — получишь публичный `https://...up.railway.app`.
4. **Обязательно подключи Volume** (Settings → Volumes → New Volume, например
   путь монтирования `/data`) — иначе локальная база паролей будет стираться
   при каждом обновлении кода, и все пароли слетят. После создания Volume
   пропиши переменную `PASSWORD_DB_PATH=/data/passwords.db`.
5. Переменные окружения нового сервиса (сайта):
   - Все те же, что у бота: `BOT_TOKEN`, `CREATOR_ID`, `LOG_CHANNEL_ID`,
     `PINGER_TELEGRAM_ID`, `GOOGLE_SHEET_ID`, `GEMINI_API_KEY`,
     `GOOGLE_CREDENTIALS_JSON_BASE64` — проще всего через
     **Railway → Shared Variables** на уровне проекта.
   - `PASSWORD_DB_PATH` — путь к базе паролей на Volume (шаг 4).
   - `INTERNAL_API_SECRET` — придумай любую длинную случайную строку, и
     пропиши **ОДИНАКОВОЕ** значение в переменных **и у бота, и у сайта**
     (это пароль для внутреннего запроса бот→сайт при /setpassword).
6. У сервиса бота — добавь переменную `WEBAPP_URL` со значением домена из
   шага 3 (например `br-panel.up.railway.app`, без `https://`) и то же самое
   `INTERNAL_API_SECRET`, что и у сайта.
7. **Мост с VK-ботом модерации (vk_moderation_bot)** — необязательно, без
   этого шага всё остальное работает как раньше:
   - И у сервиса бота, и у сервиса сайта пропиши `VK_BOT_API_URL` (адрес
     сервиса VK-бота на Railway, без `https://` и без слэша на конце) и
     `SITE_BRIDGE_SECRET` (любая длинная случайная строка) — оба значения
     должны совпадать с тем, что задано у VK-бота (см. его `.env.example`:
     `SITE_API_URL`, `SITE_BRIDGE_SECRET`).
   - Дальше при назначении роли (Лидер/Следящий/Старший следящий/Руководство)
     и при выдаче баллов/наказаний бот и сайт будут слать в VK-бот запрос на
     объявление в нужных "инфо-беседах" — см. `services/vk_bridge.py`.

## Локальный запуск (для проверки перед деплоем)

```
pip install -r requirements.txt --break-system-packages
uvicorn webapp.app:app --reload
```

Открой `http://localhost:8000/login`. Локально /setpassword от бота до сайта
не достучится (WEBAPP_URL будет указывать на Railway, а не на localhost) —
для чисто локальной проверки интерфейса можно временно вставить пароль прямо
в базу через python:
```python
from webapp.db import set_password_hash
from utils.passwords import hash_password
set_password_hash(ТВОЙ_TELEGRAM_ID, hash_password("тест1234"))
```
